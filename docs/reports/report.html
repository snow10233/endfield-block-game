Endfield Block Game 報告準備說明

這份文件是報告前複習用，比簡報版更詳細。重點是讓我能講清楚專案怎麼設計、 怎麼實作，以及 AI 在開發中扮演什麼角色。

一句話介紹：這是一個以《明日方舟：終末地》「源石電路修復」為靈感的拼圖小遊戲， 玩家放置多邊形零件，讓每列與每行的指定顏色格數符合提示；C++ 後端負責所有規則， Electron + Vue 前端負責畫面與互動。

1. 專案動機與技術選擇

本專案的玩法接近 Nonogram，但不是用滑鼠直接塗格子，而是要把不同形狀的多邊形零件放到棋盤上。 棋盤旁邊會顯示每一列、每一行需要的顏色格數；只要所有列和行的數量都剛好符合，就判定過關。

為什麼不用同一套工具

上一次作業五子棋是用 PyQt。這次我想嘗試不同的桌面應用開發方式，所以沒有繼續使用同一套工具。 另外，Qt 的 QSS 當然可以做介面，但 CSS 的資料、範例和 AI 訓練資料都更豐富，對於快速調整 UI 會比較方便。

為什麼不用遊戲引擎

這個專案不是要做複雜場景、物理、關卡串接或角色系統，而是偏向 UI、狀態顯示和拖曳互動。 我對遊戲引擎本身也沒有特別想深入，所以選擇用一般桌面應用框架來做。

Electron、Vue、TypeScript 的理由

選擇 原因
Electron 可做桌面應用，也能延伸到未來工具型或介面型專案，不只限於遊戲。
Vue 3 本專案前端狀態不算非常複雜，Vue 對這種互動畫面較直觀，開發成本較低。
TypeScript 用型別定義前後端資料，例如 GameState、MovablePiece、PlaceResponse，降低欄位與型別錯誤。
C++20 符合課程要求，也讓遊戲規則、勝利判定和 solver 集中在後端。
報告時可以自然說明：我原本不熟 Vue，這次主要把 Vue 當作 Electron 的 UI layer 來學。 核心規則和資料流是我先定好的，前端 component、CSS、互動細節有大量使用 Claude Code 輔助完成。 我理解本專案的 Vue 資料流，但不會說自己已經精通 Vue 生態。

2. 專案架構設計

endfield-block-game/
├── backend/      C++20 + CMake
├── frontend/     Electron + Vue 3 + TypeScript
└── docs/         規則、介紹與報告文件

這個專案最重要的設計原則是：C++ 後端是遊戲邏輯的唯一真相來源。 前端可以做視覺預覽，但真正能不能放置、是否過關、關卡是否有解，都由 C++ 判斷。

整體資料流

Vue renderer ↓ 呼叫 api/backend.ts preload bridge: window.api.backend.call() ↓ ipcRenderer.invoke('backend:call') Electron main process ↓ child.stdin.write(JSON line) C++ backend process ↓ stdout 回傳 JSON line Electron main process 依 id 找回 Promise ↓ Vue store 更新 state，畫面重新渲染

Electron 與 C++ 的 IPC

Electron main process 位於 frontend/src/main/index.ts。它用 spawn() 啟動 backend/build/main，再用 readline 一行一行讀取後端 stdout。格式是 NDJSON，也就是一行一個 JSON 物件。 

{"id":1,"op":"place","pieceId":0,"row":0,"col":0,"rot":0}
{"id":1,"ok":true,"won":false}

每個 request 都有 id，Electron main process 用這個 id 管理 pending Promise。 C++ 回傳同樣的 id 時，就可以把 response 對回原本的呼叫。

責任切分

層級 檔案位置 負責內容
C++ backend backend/include, backend/src 關卡解析、棋盤資料、放置規則、勝利判定、solver、關卡可解性驗證。
Electron main frontend/src/main/index.ts 建立視窗、啟動 C++ process、管理 IPC、檔案開啟與存檔對話框。
Preload frontend/src/preload/index.ts 用 contextBridge 暴露安全 API 給 renderer。
Vue renderer frontend/src/renderer/src 畫面顯示、拖曳互動、提示 overlay、音效、關卡設計器 UI。

拖曳過程的特殊設計

拖曳時 mousemove 很頻繁。如果每一幀都送 IPC 到 C++，會讓互動變卡。因此拖曳中的視覺跟隨、 旋轉動畫與紅綠預覽由前端處理；滑鼠放開時，前端只送最終格子座標給 C++。C++ 回傳成功或失敗後， 前端再刷新完整 GameState。

3. 開發順序

這次開發是由核心資料流到完整體驗，先確保後端資料正確，再接前端顯示，最後補互動與視覺效果。

  1. 先實作後端關卡讀取，並讓後端能輸出對應 JSON 狀態。
  2. 接著實作前端基本畫面，並提供載入關卡的 GUI。
  3. 再實作遊戲放置邏輯、旋轉、移除，以及勝負判定。
  4. 接著實作關卡生成器，讓使用者能設計棋盤、提示數字、固定格與零件。
  5. 最後補上音效、BGM、背景圖與動畫，讓展示成果更完整。
後端 parser → JSON state → 前端渲染 → place/remove/reset → solver/autoSolve → LevelDesigner → 可解性驗證 → 音效、BGM、背景圖、動畫

4. 重點功能說明

後端核心資料

模組 功能
Cell 定義棋盤格狀態：Empty、Blocked、Fixed、Movable。
Board 保存二維棋盤，提供 resize、inBounds、at。它只管資料，不直接決定規則。
Part 保存零件 id、顏色、原始形狀、旋轉、是否已放置、目前座標。
GameDataPacket 保存關卡資料，包括顏色數、棋盤大小、row/col 目標、fixed 格、blocked 格與零件。
Game 規則核心，負責 load、reset、place、remove、isWon、目前 row/col filled count。

關卡文字格式讀取

FileLoader::parse() 從純文字讀取關卡。格式依序包含顏色數、棋盤大小、 每個顏色的 row/col 目標、固定有色格、不可放置格，以及多個可移動零件。 

colors rows cols

每個 color:
  rowNeed[0..rows-1]
  colNeed[0..cols-1]
  fixedCount
  fixedRow fixedCol ...

nonColorFixedCount
blockedRow blockedCol ...

每個 movable part，直到 EOF:
  color partRows partCols
  shape rows...

放置、旋轉與合法性

零件的形狀存在 Part::baseShape_，旋轉值是 0..3， 每次代表順時針 90 度。前端拖曳時也會用同樣的旋轉概念產生預覽，但真正的合法性判斷在 Game::canPlace()。

canPlace() 會檢查越界、blocked、fixed、其他 movable 零件重疊。成功才呼叫 writePieceCells() 把零件寫進棋盤。

列行數量與過關條件

Game::isWon() 會對每個顏色檢查所有 row 和 col。判定條件不是大於等於， 而是目前填色數必須剛好等於關卡需求。只要有一列或一行不符合，就還沒過關。

Solver / AI 幫你放

Solver 使用回溯法。它會先把固定格與 blocked 格放到暫存棋盤， 再產生每個零件的不重複旋轉。搜尋時大零件優先，並且每次放置都先檢查 row/col 是否超過目標， 這樣可以提早剪枝。

前端按鈕 後端 op 效果
提示 solve 只回傳解答座標，前端在棋盤上畫 hint overlay，不改變棋盤。
AI幫你放 autoSolve C++ 找到解後 reset 棋盤，再逐一呼叫 placePart() 套用解答。

關卡設計器與可解性驗證

LevelDesigner.vue 可以調整棋盤大小、顏色數、row/col 目標、blocked 格、fixed 格， 也能新增與編輯零件。它會把目前設計輸出成和 FileLoader 相容的文字格式。

設計器會呼叫 validateLevelString。後端會先 parse 文字，再用 Solver 確認是否有解。 有解時才允許輸出文字與存檔。

前端拖曳互動與放置預覽

GameBoard.vue 負責棋盤、row/col indicator、放置預覽和 hint overlay。 DragLayer.vue 負責讓正在拖曳的零件跟著滑鼠移動，按 R 可以旋轉。 store/drag.ts 保存拖曳中的 pieceId、顏色、形狀、旋轉與滑鼠位置。

前端 preview 會用目前棋盤資料估算可否放置，顯示綠色或紅色。但這只是給使用者看的提示。 最終仍要靠 C++ place response 決定。

音效、BGM、背景圖與動畫

前端資源位於 frontend/resources。目前包含 BGM、背景圖，以及按鈕、放置、旋轉、過關等音效。 store/audio.ts 會管理背景音樂、音效快取、靜音狀態與 localStorage。

6. 如何配合 AI 實作

本次開發主要使用 Claude Code 作為 coding agent。我的定位不是讓 AI 完全主導專案， 而是把它當作加速開發、跨語言串接、UI 調整與文件整理的工具。

實際協作流程

  1. 先閱讀作業規格，確認 C++ 後端必須負責核心遊戲邏輯。
  2. 開發初期先建立基本後端架構，例如 board、part、file-loader 等資料結構，避免後續架構跑偏。
  3. 接著用自然語言描述每一階段想完成的功能，請 Claude Code 協助補齊前端、後端、IPC 與 UI。
  4. 必要時先和 AI 討論實作方向，再請它修改程式。
  5. 完成後自己檢查程式結果，透過執行或操作遊戲確認功能是否符合需求。
  6. 如果行為不符合預期，再補充描述讓 AI 繼續修正。
  7. 開發過程中也讓 AI 協助整理架構說明與報告文件。

前端 Vue 的誠實說法

我原本不熟 Vue，因此前端 component、CSS 排版、拖曳互動細節大量使用 Claude Code 輔助。 但前端在本專案中的定位很清楚：只負責 UI、輸入與顯示，不負責核心遊戲規則。

報告時重點不是假裝我精通 Vue，而是要能講清楚資料怎麼流： renderer → preload → Electron main → C++ backend → state 回傳 → Vue 更新畫面。

AI 協作反思

  • AI 很適合加速樣板程式、UI 調整、文件整理與跨語言串接。
  • 人仍然需要掌握架構方向，尤其是 C++ 後端必須負責規則這件事。
  • AI 產出的內容需要由人檢查，不能完全不看就接受。
  • 本專案規模適中、需求清楚，因此和 AI 協作過程相對順利。

我需要會回答的問題

狀態放在哪裡？

回答方向：前端狀態主要在 frontend/src/renderer/src/store/game.ts。 它用 Vue 的 ref 和 computed 做簡單 store，沒有使用 Pinia。 state 保存後端回傳的 GameState，另外也保存錯誤訊息、提示狀態、solver 解答、 是否正在套用解答、目前關卡載入時間等。

可以補一句：真正的遊戲規則狀態仍然以 C++ 為準，前端 store 是用來顯示後端回傳資料。

前端怎麼跟 C++ 溝通？

回答方向：Vue renderer 先呼叫 api/backend.ts，它會再呼叫 preload 暴露的 window.api.backend.call()。preload 用 ipcRenderer.invoke('backend:call') 傳到 Electron main process。main process 再把 JSON request 寫進 C++ child process 的 stdin。 C++ 用 stdout 回傳 JSON line，main process 依照 id 對回 Promise，最後 Vue 更新畫面。

Vue component/store → api/backend.ts → window.api.backend.call() → ipcRenderer.invoke('backend:call') → Electron main → C++ stdin/stdout → response 回到 Vue
拖曳時為什麼不每次都問 C++？

回答方向：mousemove 太頻繁，每一幀都 IPC 會造成卡頓。所以拖曳中的視覺預覽由前端處理， 包含跟隨滑鼠、旋轉和紅綠預覽；滑鼠放開時才送最終座標到 C++ 做合法性判斷。 這樣保留互動流暢度，也保留 C++ 作為規則權威。

Vue 在這個專案的角色是什麼？

回答方向：Vue 只負責畫面和互動，不負責核心遊戲規則。像 GameBoard.vue 畫棋盤與提示， PiecePanel.vue 顯示零件欄，DragLayer.vue 處理拖曳浮層， LevelDesigner.vue 做關卡設計器 UI。是否能放置、是否過關、solver 結果都由 C++ 判斷。

TypeScript 在這個專案幫了什麼？

回答方向：TypeScript 用 frontend/src/renderer/src/types/level.ts 定義資料形狀，例如 GameState、MovablePiece、PlaceResponse、 SolveResponse。這樣前端和 AI 都比較不容易把欄位名稱或型別搞錯。

例如 MovablePiece.row 和 MovablePiece.col 是旋轉後 bounding box 左上角座標， rotation 是 0..3。這些用型別寫清楚後，資料流比較穩定。

如果被問「你會 Vue 嗎」要怎麼回答？

回答方向：我原本不熟 Vue，但透過這個專案理解了 Vue component、reactive state、 computed 與事件處理在本專案中的用途。我不會說自己精通 Vue 生態， 但能說明本專案前端資料流與各元件責任。

可以補一句：本次作業重點是 C++ 遊戲邏輯，前端主要是 UI layer，所以使用 AI 輔助 Vue/CSS 實作是合理的技術取捨。

關卡設計器怎麼確定關卡有解？

回答方向：LevelDesigner.vue 會把目前設計組成文字格式，然後呼叫 validateLevelString。C++ 後端先用 FileLoader 解析，再用 Solver 嘗試找解。找得到解才允許輸出與存檔。

solver 的方法是什麼？

回答方向：solver 使用回溯搜尋。它會保留 fixed 和 blocked 格，對每個零件產生不重複旋轉， 大零件優先放。每次放置會檢查是否越界、是否重疊，以及該顏色 row/col 是否超過目標。 全部零件放完後，再檢查所有 row/col count 是否剛好等於目標。

為什麼說 C++ 是唯一真相來源？

回答方向：因為前端不決定最後放置結果，也不決定過關。前端只能送 request 給後端， 後端的 Game::placePart() 和 Game::isWon() 才會更新規則狀態。 前端每次成功操作後都會呼叫 state() 重新拿完整狀態並渲染。

8. 總結與反思

這次專案主要收穫是學到 Electron / Vue 與 C++ backend 的整合方式。透過把規則集中在 C++， 前端就可以專心處理畫面、輸入、拖曳預覽、音效與檔案對話框，責任切分比較清楚。

AI 協作讓開發速度變快，尤其在前端 UI、IPC 串接與文件整理上很有幫助。 但前提是自己要先理解架構與規則，否則 AI 可能會把不該放在前端的規則搬到 TypeScript。

對於自己不熟的 Vue / CSS，也可以透過 AI 輔助快速完成；但我需要清楚知道前端只是 UI layer， 核心規則仍然由 C++ 後端負責。這是本專案最重要的設計邊界。
