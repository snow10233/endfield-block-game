## 1. 專案動機與技術選擇

請說明這是一個以《明日方舟：終末地》「源石電路修復」為靈感的拼圖小遊戲。玩法接近 Nonogram，玩家需要把多邊形零件放到棋盤上，讓每列與每行的指定顏色格數符合提示。

請補充以下技術選擇理由：

- 上一次作業五子棋是使用 PyQt，這次希望嘗試不同的桌面應用開發方式。
- 不使用遊戲引擎的原因：自己對遊戲引擎本身興趣不大，而且這個專案更偏向 UI、狀態顯示與互動設計，不一定需要完整遊戲引擎。
- 選擇 Electron 的原因：想學習更通用的桌面應用框架，未來也比較可能用在其他工具型或介面型專案。
- 不繼續使用 Qt 的原因：一方面是想多學新工具，另一方面 CSS 相關資料與 AI 訓練資料比 QSS 豐富，較容易透過 AI 協作快速調整畫面。
- 選擇 Vue 而非 React 的原因：本專題狀態轉移不算非常複雜，Vue 對這類互動畫面來說較直觀，開發成本較低。
- 選擇 TypeScript 而不是 JavaScript 的原因：TypeScript 在現代前端專案中更主流，也能用型別把前後端傳遞的資料結構寫清楚，降低把字串、數字、布林等型別搞錯的機率。尤其和 AI 協作時，TypeScript 的型別可以減少 AI 寫出「本來應該是字串卻塞數字」這類 JavaScript 鬼故事。

請在簡報中可以坦承：

> 我原本不熟 Vue，這次主要把 Vue 當作 Electron 的 UI layer 來學。核心規則和資料流是我先定好的，前端 component、CSS、互動細節有大量使用 Claude Code 輔助完成。我理解這個專案中 Vue 負責什麼、資料怎麼流、前端怎麼呼叫 C++，但不會說自己已經很熟 Vue 生態。

這段不要寫得像缺點，而是寫成合理的技術取捨：本次作業重點是 C++ 遊戲邏輯，前端主要是 UI 呈現與互動，因此用 AI 輔助 Vue/CSS 實作是合理的。

## 2. 專案架構設計

請說明 repo 分成兩個主要部分：

```text
backend/   C++20 + CMake
frontend/  Electron + Vue 3 + TypeScript
```

架構重點：

- C++ 後端負責所有遊戲邏輯，是遊戲規則的唯一真相來源。
- 前端只負責畫面顯示、使用者輸入、拖曳互動、音效與檔案對話框。
- Electron main process 會啟動 C++ backend process。
- 前後端透過 stdin/stdout 傳 NDJSON，也就是一行一個 JSON 物件。
- 每個 request 都有 `id`，方便 Electron main process 對應後端 response。
- 拖曳過程中的即時視覺跟隨由前端處理；真正放置時才把最終座標送到 C++ 判斷是否合法。

請說明這樣設計的好處：

- 符合 C++ 負責核心邏輯的要求。
- 避免把規則散落在前端，降低前後端狀態不一致的風險。
- 拖曳時不需要每一幀都跨 process 呼叫，互動比較順。
- Electron 負責桌面應用與 UI，C++ 負責規則判斷，責任切分清楚。

## 3. 開發順序

請依照以下實際開發順序撰寫：

1. 先實作後端關卡讀取，並讓後端能輸出對應 JSON 狀態。
2. 接著實作前端基本畫面，並提供載入關卡的 GUI。
3. 再實作遊戲放置邏輯、旋轉、移除，以及勝負判定。
4. 接著實作關卡生成器，讓使用者能自己設計棋盤、提示數字、固定格與零件。
5. 最後補上音效、BGM、背景圖與動畫，讓整體展示更完整。

請將這段寫成「由核心資料流到完整體驗」的開發流程：先確保後端資料正確，再接前端顯示，最後補上互動細節與視覺效果。

## 6. 如何配合 AI 實作

本次開發主要使用 Claude Code 作為 coding agent 輔助開發。請把 AI 描述成「加速開發與整理文件的工具」，不要寫成 AI 完全主導整個專案。

實際流程可以這樣描述：

- 我先閱讀作業規格，確認 C++ 後端必須負責核心遊戲邏輯。
- 開發初期先手動建立基本後端架構，例如 board、part、file-loader 等資料結構，避免後續架構跑偏。
- 接著用自然語言描述每一階段想完成的功能，讓 Claude Code 協助補齊前端、後端、IPC 與 UI。
- 必要時會先和 AI 討論實作方向，再請它修改程式。
- 完成後我會檢查程式結果，並透過執行或操作遊戲確認功能是否符合需求。
- 如果發現行為不符合預期，再補充描述讓 AI 繼續修正。
- 開發過程中也會讓 AI 協助整理架構說明與報告文件。

請不要寫「有保存完整 prompt log」或「建立專門 prompt 資料夾」，因為這次沒有真的保存 prompt。可以自然地寫成「以臨時提示與反覆修正的方式和 AI 合作」。

請特別補充 Vue / 前端這塊的誠實說法：

- 我原本不熟 Vue，因此前端 component、CSS 排版、拖曳互動細節大量使用 Claude Code 輔助。
- 但前端在本專案中的定位很清楚：只負責 UI、輸入與顯示，不負責核心遊戲規則。
- 我需要能講清楚資料怎麼流，而不是假裝自己精通 Vue。
- 報告中可以說「我知道 Vue 在這個專案扮演什麼角色，也理解 renderer -> preload -> Electron main -> C++ backend -> state 回傳 -> Vue 更新畫面的資料流」。
- 如果助教問 Vue 細節，回答重點應該放在本專案實際使用到的部分，例如 `ref`、`computed`、component、store module、事件處理，而不是泛談 Vue 生態。

可以強調以下觀點：

- AI 很適合用來加速樣板程式、UI 調整、文件整理與跨語言串接。
- 人仍然需要掌握架構方向，尤其是 C++ 後端必須負責規則這件事。
- AI 產出的內容需要由人檢查，不能完全不看就接受。
- 本專案因為規模適中、需求清楚，因此和 AI 協作過程相對順利，沒有遇到太大的阻礙。

請在 HTML 說明中特別加入「我需要會回答的問題」小節，至少包含：

- 狀態放在哪裡？
  - 回答方向：前端使用 `store/game.ts`，用 Vue 的 `ref` / `computed` 做簡單 store，沒有使用 Pinia。
- 前端怎麼跟 C++ 溝通？
  - 回答方向：Vue renderer 呼叫 `api/backend.ts`，經過 preload 暴露的 `window.api.backend.call()`，再到 Electron main process，最後用 stdin/stdout 傳 JSON 給 C++。
- 拖曳時為什麼不每次都問 C++？
  - 回答方向：mousemove 太頻繁，每幀都 IPC 會卡，所以拖曳中的視覺預覽由前端處理；滑鼠放開時才送 C++ 做合法性判斷。
- Vue 在這個專案的角色是什麼？
  - 回答方向：Vue 只負責畫面和互動，不負責核心遊戲規則。
- TypeScript 在這個專案幫了什麼？
  - 回答方向：用 `types/level.ts` 定義 `GameState`、`MovablePiece`、`PlaceResponse` 等資料形狀，讓 AI 和人都比較不容易把欄位或型別搞錯。
- 如果被問「你會 Vue 嗎」要怎麼回答？
  - 回答方向：我原本不熟 Vue，但透過這個專案理解了 Vue component、reactive state、computed 與事件處理在本專案中的用途；我不會說自己精通 Vue，但能說明本專案前端資料流與各元件責任。

## 8. 總結與反思

請用自然語氣總結：

- 這次專案主要收穫是學到 Electron / Vue 與 C++ backend 的整合方式。
- 透過把規則集中在 C++，讓前後端責任更清楚。
- AI 協作讓開發速度變快，尤其在前端 UI、IPC 串接與文件整理上很有幫助。
